# M7 — Blackmagic IP10 codec (2160p59.94/60 over 10G)

## Why

Uncompressed 2160p 4:2:2 10-bit at 59.94/60p is ~12 Gbps on the wire — it does not fit a 10G link.
Blackmagic's receivers (2110 IP Converter, DeckLink IP) therefore accept those two rates **only** as
**Blackmagic IP10**, an open, license-free codec. This branch lets the Spark engine emit IP10 so its
processed 2160p60 output can be received by Blackmagic gear, toggled by a single dashboard checkbox.

Reference: Blackmagic's published "Blackmagic IP10 Codec v1.1" developer documents (spec + ANSI-C
reference + a conformance vector). Those assets are Blackmagic-proprietary and are **not committed**;
our implementation is clean-room from the public algorithm and validated against the vector locally.

## What IP10 is

A Context-Adaptive, Absolutely-Constant-Bit-Rate (ACBR) codec. Every 10-bit sample is mapped to a
fixed-size **8-bit** symbol (no variable-length codes, no buffers — tiny in hardware). The "10:8"
flavour:

- The top symbol bit flags lossless (`0`) vs lossy (`1`); the low 7 bits enumerate the value.
- A **code table** positions a 128-wide lossless window; it is chosen **only from the previously
  decoded sample**, so encoder and decoder stay in lockstep with no side channel.
- Lossless on smooth gradients; strictly bounded **±3** error on edges (perceptually masked). ~67 dB
  PSNR on the reference clip.
- Context resets at the **start of every row** (so rows are independent). Within a 4:2:2 row, luma
  references the previous **same-parity** Y (the two Y of a pgroup are independent sub-lanes, "2-back")
  and chroma references the previous Cb/Cr ("1-back").

## How it maps onto ST 2110

Per the spec, IP10 10:8 reuses the **ST 2110-20 raw payload as if it were 8-bit 4:2:2** — each codeword
sits in the equivalent 8-bit component slot of the RFC 4175 pgroup `{Cb,Y0,Cr,Y1}` (4 octets / 2 px,
vs 5 for 10-bit). So the existing packetizer transmits it unchanged once the pgroup geometry is 8-bit.

The SDP advertises the codec (ST 2110-22 framing):

```
a=rtpmap:96 vnd.blackmagic-design.ip10/90000
a=fmtp:96 sampling=YCbCr-4:2:2; depth=10; width=3840; height=2160; exactframerate=60000/1001; colorimetry=BT709; SSN=ST2110-22:2022; TP=2110TPN; scheme=10:8;
```

Note `depth=10` is the **source** depth; the payload octets are 8-bit. `PM` is omitted (defaults to
`2110GPM`). `scheme` is optional (defaults to `10:8`). **Codec name:** use the *hyphenated*
`vnd.blackmagic-design.ip10` — that's what the spec's real-device example SDP uses and what a Blackmagic
receiver accepts; the spec prose's un-hyphenated `vnd.blackmagicdesign.ip10` is rejected on the wire with
"SDP parsing" (confirmed against a BiDirect-2, 2026-06-23).

## Enabling it

**Output (Spark → Blackmagic):**
- **Dashboard:** tick **Blackmagic IP10 codec**, set output 3840×2160, Save, Start.
- **API:** `POST /api/config` with `{"ip10": true, "outWidth": 3840, "outHeight": 2160, ...}`.
- **Engine directly:** `SPARK_IP10=1 SPARK_OUT_W=3840 SPARK_OUT_H=2160 ./engine/build/st2110_pipeline`.

NMOS routing preserves `ip10` (it's an operator-set field; `reconcile()` only rewrites the source). The
node's `NodeStateSync` mirrors the daemon's `ip10` into the video sender SDP within ~3 s (same path as
output resolution and the PTP grandmaster), so the manifest a Blackmagic receiver fetches is IP10.

**Input (Blackmagic → Spark):**
- **NMOS (recommended):** just route an IP10 source to our video receiver — `parse_video_fmtp`
  auto-detects IP10 from its SDP (`vnd.blackmagicdesign.ip10` / `scheme=10:8`) and sets `inIp10`, so the
  engine RX decodes it. The receiver advertises the IP10 media type so the IS-05 PATCH is accepted.
- **Manual:** tick **Source is IP10** (Advanced), or `inIp10: true`, or `SPARK_IN_IP10=1`.

Input and output codecs are independent — Spark can receive IP10 and send raw (e.g. 2160p60 IP10 in →
downscale → 1080p raw out), or the reverse.

## Validation

- **Codec byte-exact vs Blackmagic's conformance vector** (`DucksTakeOff`, all 4,147,200 samples),
  proven for **both** the CPU reference and the **CUDA** kernel on the GB10 (sm_121). Max error ±3,
  ~67 dB PSNR, ~4% of samples lossy (edges only), idempotent on re-encode.
- **Framing round-trip** for the 8-bit IP10 geometry (`test_rtp_st2110`).
- **SDP** confirmed by tracing nmos-cpp's `make_rtpmap`/`make_fmtp` — the overridden rtpmap/fmtp are
  serialized verbatim, matching the spec example.
- Engine (`st2110_pipeline`, `spark_codec`), daemon, and NMOS node all build; `ctest` green
  (`ip10_codec`, `rtp_st2110`, `pixel_codec`, `net_addr`, `audio_st2110`).

To re-run the conformance check, point a local copy of Blackmagic's vector at the scratchpad validator
(`ip10_validate.cpp` / `ip10_gpu_test.cu`); the vector itself is intentionally not in the repo.

## Hardware validation

**TX validated end-to-end against a Blackmagic BiDirect-2, 2026-06-23.** Chain: BiDirect-1 1080p29.97
raw → Spark (upscale 2160 + FRC 30→60 + IP10) → 2160p59.94 IP10 → BiDirect-2's video receiver. BiDirect-2
accepted our SDP (IS-05 PATCH HTTP 200), the active transport file is our `vnd.blackmagic-design.ip10`
stream, and the receiver subscription is active; our side ran clean (rxLost 0, txPastErr 0, txFutureErr 0,
FRC interpolating). The `SPARK_MAX_MS` change (below) lets it run continuously instead of self-stopping
at 120 s.

Operational notes from the bring-up:
- **TX egress source IP must match the SDP `source-filter`** — Blackmagic receivers do source-specific
  (SSM) joins, so if the engine's `SPARK_TX_SRC` differs from the SDP source they silently filter every
  packet and show **black** (subscription still reports active!). The NMOS bridge now drives `txSrc` from
  the sender's resolved `source_ip` so they always agree; the engine default (`192.168.50.10`) is only for
  manual non-NMOS runs. This was the actual cause of the first black screen.
- **Run time:** `st2110_pipeline` defaults to run-until-stopped; set `SPARK_MAX_MS>0` only to bound a test.
- **PTP:** the BMD validates ts-refclk against the GM it's locked to; slave our box to the same GM
  (`deploy/ptp.sh slave`) before routing or the BMD reverts the source.
- **Blackmagic NMOS is fragile:** a rejected/malformed SDP PATCH (or an active subscription to a stream it
  can't receive) can wedge the BMD's NMOS service (500 on all endpoints, including `/self`, while the box
  still pings) — recover with a device reboot. The media plane is independent: an already-active
  subscription keeps receiving even while the BMD's NMOS API is wedged.
- **Don't `pkill` the control daemon while the engine runs** — the engine child is orphaned (keeps the NIC
  + DPDK lock), blocking the next launch. `/api/stop` first, then restart the daemon.

## Not done yet

- **RX from a real BMD IP10 source** — the decode path is code-complete and the kernel is byte-exact, but
  it wasn't exercised on hardware (no BMD was sourcing IP10 during the bring-up). If nmos-cpp rejects a
  BMD IP10 SDP at the IS-05 PATCH, route via direct `/api/config` (`inIp10` + rx group/port).
- **GPU encoder/decoder** are row-parallel (height threads) — ample for 2160p60, but could be split per
  sub-lane if a higher-rate format ever needs it.
